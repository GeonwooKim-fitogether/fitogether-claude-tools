# /goal-prompt — 무인 작업 지시서를 만든다

> **한 줄 요지:** 너는 지금 `/goal`을 실행하는 것이 아니라, **`/goal`에 넣을 지시서 한 장을 만들어 사용자에게 건네는 일**을 한다. 완료 기준과 상한이 빠진 지시서는 며칠을 헛돌 수 있으므로, 네 블록을 빠짐없이 채우는 것이 이 커맨드의 전부다.

이번에 무인으로 맡기려는 목표는 다음과 같다:

**$ARGUMENTS**

---

## 딛고 서는 기준

이 저장소의 `.claude/rules/` 규칙이 세션 시작 시 자동으로 로드되어 네 컨텍스트에 이미 들어와 있다. 그중 둘이 이 커맨드를 직접 구속한다.

- [`stake-calibration.md`](../rules/stake-calibration.md) — `/goal`을 언제 쓰는지 정한 규정. 발동 조건 둘(사용자의 명시 요청 · 사람 관문 작업 제외)은 아래 0절에서 네가 확인한다.
- [`escalation.md`](../rules/escalation.md) §2 — 사람 관문 여섯. 골 범위에서 빼야 하는 것이 무엇인지의 정본이다.

## 0. 먼저 확인 — 이 일이 `/goal`에 맞는가 (통과 못 하면 지시서를 쓰지 않는다)

지시서를 쓰기 전에 셋을 확인한다. 하나라도 걸리면 **지시서를 쓰지 말고 그 사실을 사용자에게 말한다.** 안 맞는 일에 지시서를 만들어 주는 것이 이 커맨드의 가장 나쁜 실패다.

1. **완료를 대화가 증명할 수 있는가.** `/goal`의 완료 판정은 작업하는 모델이 아니라 **별도의 작은 모델(평가자)** 이 매 턴 내리는데, 그 평가자는 도구를 쓰지 못하고 **대화에 이미 드러난 것만** 본다. 그래서 "화면이 보기 좋아지면"처럼 사람 눈으로만 확인되는 조건은 영원히 판정 불능이다. 명령의 실행 결과가 대화에 남는 형태여야 한다.
2. **사람 관문이 범위 안에 있지 않은가.** 골이 도는 동안 사람은 개입하지 않는다. 보안·라이브 데이터베이스 쓰기·비용 발생·main 머지·되돌리기 어려운 구조 선택이 범위 안에 있으면 그 부분을 **범위에서 빼거나**, 골을 그 직전까지로 끊는다.
3. **판돈이 이만한 도구를 부를 만한가.** 한두 번의 도구 호출로 끝날 일이라면 `/goal`이 아니라 그냥 하면 된다. 이것도 판돈 규칙이 말하는 과잉 엔진이다.

## 1. 지시서 서식 — 네 블록, 하나도 비우지 않는다

아래 형태로 만든다. 사용자가 그대로 복사해 `/goal <내용>`으로 붙여 넣을 수 있어야 하므로, **설명을 섞지 말고 지시서 자체만** 코드 블록에 담아 낸다.

```text
[목표]
무엇을 이루면 끝인지 한 문장. 수단이 아니라 결과로 쓴다.

[작업 원칙]
- 지켜야 할 제약. 무엇을 바꾸면 안 되는지를 포함한다.
- (예: 테스트 파일 외의 소스는 고치지 않는다 / 의존성을 새로 추가하지 않는다)

[수행 단계]
1. 먼저 무엇을 확인하고
2. 그다음 무엇을 하고
3. 막히면 무엇을 시도하는지
   — 순서가 강제되는 것만 적는다. 세세한 지시는 오히려 방해다.

[완료 기준]
- 측정 가능한 종결 상태 하나: (예) test/auth 의 테스트가 전부 통과한다
- 그것을 어떻게 증명하나: (예) `npm test` 가 종료 코드 0 으로 끝난다
- 지켜져야 할 것: (예) 다른 테스트 파일은 수정되지 않는다
- 상한: (예) 위 조건을 만족하거나, 20턴이 지나면 중단한다
```

## 2. 완료 기준을 쓰는 법 (여기가 이 지시서의 척추다)

세 요소를 모두 넣는다. 하나라도 빠지면 골이 언제 끝나는지가 모호해진다.

| 요소 | 무엇을 적나 | 나쁜 예 → 좋은 예 |
|---|---|---|
| **측정 가능한 종결 상태** | 예·아니오로 답할 수 있는 상태 하나 | "코드가 좋아진다" → "타입 검사에 오류가 0건이다" |
| **증명 방법** | 그것을 무엇으로 보이나 | (없음) → "`npx tsc --noEmit` 이 종료 코드 0 으로 끝난다" |
| **불변 제약** | 가는 길에 바뀌면 안 되는 것 | (없음) → "기존 테스트가 하나도 깨지지 않는다" |

## 3. 상한은 선택이 아니라 필수다

**모든 지시서에 턴 또는 시간 상한을 반드시 넣는다.** `/goal`은 기본적으로 제한 없이 돌기 때문이다. 상한은 완료 기준 안에 한 줄로 적는다 — "위 조건을 만족하거나, 20턴이 지나면 중단하고 그때까지의 상태를 보고한다."

상한을 정하는 감각은 이렇다. 반복이 명확한 작업(오류 목록을 하나씩 없애는 일)은 대상 개수의 두 배쯤, 탐색이 필요한 작업은 짧게 잡고 한 번 끊어 본 뒤 다시 거는 편이 안전하다.

## 4. 건네는 법 — 지시서만 주지 말고 셋을 함께 말한다

지시서를 낸 뒤 아래 세 줄을 덧붙인다. 받는 사람이 그대로 실행할 수 있어야 한다 (communication 규칙 8-2의 부탁 서식).

- **어디서:** 이 저장소를 연 Claude Code 세션에서.
- **무엇을:** `/goal` 뒤에 아래 지시서를 붙여 넣고 실행한다. 도구 승인 창이 매 턴 뜨는 것을 피하려면 권한 모드를 자동으로 두고 시작한다.
- **무엇이 보이나:** 목표가 도는 동안 `◎ /goal active` 표시가 뜨고, 매 턴 평가자의 판정 이유가 남는다. `/goal`만 입력하면 현재 상태(경과·턴 수·토큰)를, `/goal clear`로 중단한다.

## 5. 절제 — 이 커맨드가 하지 않는 것

- **골을 대신 실행하지 않는다.** 지시서를 만들어 건네는 데까지가 이 커맨드의 일이다. 실행은 사용자가 판단해 건다.
- **완벽한 지시서를 혼자 지어내지 않는다.** 목표가 모호하면 지시서를 억지로 채우지 말고, 결과를 가르는 갈림길 한둘을 사용자에게 먼저 묻는다. 잘못 세운 목표에 정교한 지시서를 만드는 것이 가장 비싼 실패다.
- **지시서가 길수록 좋은 것이 아니다.** 수행 단계는 순서가 강제되는 것만 적는다. 조건 자체는 4,000자를 넘을 수 없다는 도구 제약도 있다.
